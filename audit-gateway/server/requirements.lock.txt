# 网关服务端依赖锁 —— requirements.txt 的可复现版本
#
# ## 这份文件是从哪来的
#
# 2026-08-27 从**测试服 192.168.30.108 上正在跑的那个 venv** `pip freeze` 出来的
# （`C:\Users\developer\Desktop\gateway\server\.venv`，Python 3.14.4），
# 不是在开发机上重新解析一遍。理由很直接：那套版本是已经跑起来、
# 且 `pip check` 干净的一套；开发机上重装一次得到的是「今天的最新」，
# 那正是 requirements.txt 不锁版本时的老问题。
#
# ## 怎么用
#
# 部署一律用这份，不要用 requirements.txt：
#
#     pip install -r requirements.lock.txt
#
# requirements.txt 保留着，它记的是「我们直接依赖什么、为什么」——
# 加一个新依赖改那份，然后重新生成这份。两份不是二选一。
#
# ## 为什么有 environment marker
#
# 上面那个 venv 是 Windows 的，freeze 出来会有两类偏差，直接照抄会在 Linux 上出错：
#
# - `colorama` / `win32_setctime` 只有 win32 才需要（loguru、click 的平台依赖）。
#   没有 marker 的话 Linux 上也会去装，装得上，但为什么装谁也说不清。
# - `uvloop` 反过来 —— `uvicorn[standard]` 在非 Windows 上才拉它，
#   所以它**不在** Windows 的 freeze 里。照抄的结果是 Linux/容器上
#   uvicorn 静默回落到 asyncio 事件循环：跑得起来，只是慢，而且不报任何东西。
#   这一条是补上去的，版本按 cp314 有 manylinux wheel 挑的（0.22.1）。
#
# ## pytest 为什么在这里
#
# 因为 requirements.txt 里就有。这份是它的锁版本，不是「生产依赖清单」，
# 保持一一对应比少装两个包重要。容器里想去掉，用 `--no-deps` 另列一份，
# 别在这份上手删 —— 手删的那次一定不会同步回 requirements.txt。
