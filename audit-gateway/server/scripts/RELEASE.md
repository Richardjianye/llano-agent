# 发布流程

## 顺序不能反：**先迁移，再上代码**

`warn_schema_drift` 在 prod 是**拒绝启动**的。新代码里模型多了一列、库里没有，
网关不是「功能不可用」，是**直接起不来**。

在 Zeabur 上尤其糟：那里**没有终端也没有 SSH**（平台的 Web 终端连不上；SSH 是
服务层面禁止的——给 root 账密就不提供容器编排了）。服务起不来之后你没有任何手段
进去补跑迁移，只能回滚代码。

所以：

```bash
# 1. 看有哪些没跑（不改库）
MIGRATE_DSN='mysql://root:***@host:port/audit_gateway' \
  python scripts/migrate.py --dry-run

# 2. 真跑
MIGRATE_DSN='...' python scripts/migrate.py

# 3. 退出码 0 之后，再推代码触发 Zeabur 构建
git push
```

**DSN 走环境变量不走命令行**：命令行会出现在 shell 历史与进程列表里。
连接信息在 `~/Desktop/llano-agent-keys` 的 `zeabur_mysql_*`（用户名 root）。

## 迁移器做对的三件事

| | 为什么 |
|---|---|
| **跟踪表 `schema_migrations`** | 每个文件按文件名记一行，跑过就不再跑。不靠「语句报错就当已应用」那种猜——那分不清「上次跑过」和「有人手工加过一个同名但类型不同的列」 |
| **建议锁 `GET_LOCK`** | Zeabur 是「起新容器 → 跑一段 → 淘汰旧容器」，两个容器会同时在线。没有锁就是两个进程同时 ALTER 同一张表 |
| **失败即退出非零** | 半截迁移比不迁移更糟。发布流程据此中止，不要接着上代码 |

### ⚠️ 迁移中途失败时

MySQL 的 DDL 是**隐式提交**的，已执行的语句**不会回滚**。而这个文件还没被记进
跟踪表，所以下次运行会从它的第一条重来。

要做的是：手工确认这个文件已经执行到哪一步，修好之后重跑。

**不要**把它手工记进 `schema_migrations` 来「跳过」——那会让库结构与代码的偏差
永久留下，而下一个人完全看不出来。

## 接管一个已经手工跑过迁移的库

跟踪表是 2026-08-31 才加的。在那之前 108 与 Zeabur 都是手工执行的，所以首次使用
要先「认账」：

```bash
# 把截至某个文件（含）的迁移记为已应用但不执行
python scripts/migrate.py --adopt-through 2026-08-26-skill-security-events.sql

# 或者全部（用于确知已全部跑过的库）
python scripts/migrate.py --adopt-through all
```

**必须显式指定，不做自动检测。** 「这张表已经存在所以大概跑过了」是猜，而猜错的
方向是致命的——真正没跑的迁移被永久跳过，且没有任何一处会报错。

认账之前先 `--dry-run`，再对着 `information_schema` 确认库里实际有哪些表/列。

## 已完成的接管（2026-08-31）

| 环境 | 动作 | 结果 |
|---|---|---|
| Zeabur | 认账至 `2026-08-26-skill-security-events.sql`，执行后 3 个 | 15/15，待执行 0 |
| 108 | 三个新文件补进 `migrations/`，`--adopt-through all` | 15/15，待执行 0 |

两边都逐列核对过（`MEDIUMTEXT` 没掉成 `TEXT`、`untrusted` 默认 1、
`usage_records` 两个新列历史行自动填上且 0 个 NULL、三个屏蔽词种子在位）。

## 开发期的现实

负责人 2026-08-31 说明：开发阶段 SQL 会经常改，功能定下来之后基本不动库。

所以现在**不做**「启动时自动跑迁移」。那套东西的价值在于「部署频繁而人不在场」，
而现在是反过来的：改得频繁，但每次都有人盯着。手动一步换来的是**每次都能先
`--dry-run` 看一眼**，这在 schema 还在变的阶段比自动化更值。

哪天迁移稳定下来、部署变成日常，再把 `migrate.py` 挂进容器启动脚本——它已经是
幂等的、带锁的，挂上去不用改。
