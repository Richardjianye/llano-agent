# 会话审计使用说明

> 面向管理部门审计员与管理层。技术实现见 `audit-gateway/server/README.md`，
> 设计决策见根目录 `TODO.md`。
>
> 本文承载的是**原本散落在界面上的解释性文案**。界面只留操作，
> 说明集中在这里 —— 逐条在页面上解释系统行为，会把真正要看的内容挤下去。

---

## 一、谁能看

会话内容的可见性**按部门授权，不按角色**（决策 #17）：

| 身份 | 能否查阅会话内容 |
| ---- | ---------------- |
| 总裁 | 无条件可以 |
| 管理部门 + 级别 ≥ 审计员 | 可以 |
| 开发者（不在管理部门） | **不可以**，哪怕拥有全部系统配置权限 |
| 部门负责人 / 员工 | 不可以 |

需要看全局内容的高管或开发者，走「划入管理部门」这条路，不给角色开后门。

⚠️ 这与**用量报表**的权限是两套独立规则：管理部门的审计员看得到全公司聊天内容，
但用量报表里他只能看本部门的数字。这不是矛盾，是刻意区分「内容」与「成本」两种视角。

## 二、看到的内容是什么

| 部分 | 存的是什么 |
| ---- | ---------- |
| 请求内容 | **发送方向脱敏后**的版本（客户端替换一遍 + 服务端兜底一遍） |
| 模型回复 | **原样留存，不做任何改动** —— 审计员看到的就是模型真实说过的话 |
| 图片 / 文件 | 抽出为独立的附件记录，正文中以 `[[attachment:…]]` 占位符表示 |

### 关于脱敏

只在**发送方向**替换公司名与品牌关键词。定位是「聊胜于无的防御纵深」，
不是匿名化 —— 项目代号、内部黑话、写作风格都能反向识别出人。
主防线是与厂商签的书面数据协议，不是这层替换。

详情页带「已脱敏」标记的，表示服务端确实命中并替换过关键词。

### 关于截断

单条内容超长（当前上限 2 万字符）会在入库时被截断，列表和详情都会显式标出。
**看到「截断」标记时，你看到的不是全部** —— 这一点会直接影响审计结论，
不要在截断的记录上下「他没说过 X」这类判断。

## 三、时间怎么读

- 所有时间都是**服务器本地时间**（部署要求服务器时区为 Asia/Shanghai）。
- 一次调用只有**一个**时间戳，就是详情页顶部显示的那个。
- **逐条消息没有各自的时间。** OpenAI 协议里的 message 不带时间戳，
  客户端每一轮都会把完整对话历史重新发一遍。所以同一段对话内容会在
  多条记录里重复出现，每条记录的时间是「这一轮请求发生的时刻」。

由此推出一条读法：想还原一段完整对话的时间线，看的是**同一个人相邻几条记录的时间**，
而不是某一条记录内部的消息顺序。

## 四、系统提示词

Agent 类客户端的系统提示词动辄几千字，且每条记录里都一模一样。
详情页里它**默认折叠**，点击展开。

折叠是因为它属于「配置」而非「对话内容」：审计要看的是员工说了什么、模型答了什么。
需要核对提示词本身时（例如排查越权指令），展开即可。

超过 600 字的普通消息也会折叠，底部渐隐提示还有内容。

## 五、附件

附件卡片有三种状态，含义完全不同：

| 状态 | 含义 | 能否看到原件 |
| ---- | ---- | ------------ |
| 正常 | 已落盘留存 | 能，点「查看原件」 |
| 未留存 | 超过单文件上限，或配置关闭了落盘 | 不能，但文件名 / 大小 / 哈希都在 |
| 远程链接 | 客户端传的是 URL 而非文件内容 | 不能，网关按设计从未抓取 |

「未留存」不等于「没发生」—— 记录仍然证明该员工在该时刻发送过这个文件。

每个附件都有 **sha256 内容哈希**，卡片上可一键复制。要证明「审计里这张图
和别处那张图是同一份」，靠的就是这个值。

## 六、检索与导出

- **关键词**至少 2 个字，在请求与回复中同时检索。跨度上限 366 天。
- **用户筛选**列出全部在职人员，不只是「有记录的」——
  「查了但没有记录」和「压根查不了」是两个完全不同的结论。
- **导出只含摘要，不含全文。** 这是刻意的：全文一旦导成本地文件，
  就彻底脱离了留存期限与访问控制的管辖。需要看全文请逐条点开。

## 七、你的查阅行为也在被记录

**每一次**检索、查看全文、查看附件、导出，都会写进查阅日志，内容包括：
谁、何时、看了谁的哪一条、用了什么筛选条件、来源 IP。

在「查阅日志」标签页可以查看。四种动作的颗粒度：

| 动作 | 记录到什么程度 |
| ---- | -------------- |
| 检索列表 | 查询条件 + 命中条数（不记具体是哪些人的记录） |
| 查看全文 | **精确到某一条会话，以及内容归属人** |
| 查看附件 | 精确到某个附件 |
| 导出 CSV | 查询条件 + 导出条数 |

查看「查阅日志」页面本身不会产生新记录 —— 否则翻两页就把真正的查阅行为淹没了。

这项设计来自决策 #8，也是上线前合规动作的一条：审计权力本身需要被约束。

## 八、常见疑问

**为什么列表里看不到全文？**
列表只给摘要，全文必须点开详情。这样「看了谁的哪一条」才能精确记进查阅日志 ——
如果列表直接带全文，日志就只能记「看了第 3 页」，事后追责基本没用。

**为什么有的记录状态是「失败」但仍然有内容？**
上游拒绝或超时的调用也会完整记录。上游抖动的频率是评估合作厂商稳定性的依据，
而失败请求里的内容同样是员工发出去过的内容。

**为什么某条记录的附件数是 0，但正文里提到了图片？**
可能是客户端传的远程链接（未抓取），也可能上游拒收了多模态请求。
查看该条的附件区与状态标记即可区分。

**审计数据保存多久？**
留存期限**先由制度文件规定，再做技术实现**。当前尚未启用自动清理，
制度落地前请勿假设数据会自动过期。
